## Design Context

### Users

Obsidian users who plan and review a day inside their notes. They use Oneday as a compact, direct-manipulation timeline: create and edit time blocks quickly, compare actual records with plans, and keep Markdown as the source of truth.

### Brand Personality

Calm, precise, native. The interface should feel like a carefully integrated Obsidian tool rather than a separate web app or decorative dashboard.

### Aesthetic Direction

Refined utility with compact controls, restrained color, and Obsidian design tokens in both light and dark themes. Highlighter colors carry semantic identity; surrounding chrome stays quiet. Avoid oversized controls, nested-card styling, custom shadows, ornamental gradients, emoji iconography, and one-off colors or spacing.

### Design Principles

1. Reuse Obsidian tokens for typography, radii, spacing, color, focus, and elevation.
2. Controls sharing a row and interaction tier must share measurable height, baseline, radius, and state treatment.
3. Keep frequently used actions compact and immediately legible; reveal layout and maintenance actions progressively.
4. Preserve direct manipulation without visual handles at rest; provide clear focus and accessible alternatives.
5. Verify UI changes in both themes and under resize, overflow, hover, active, and scrolling states.

## Oneday UI Tokens

The implementation exposes a small semantic token layer on `.oneday-container`.
Component CSS must consume these roles instead of introducing one-off radii or
neutral grays.

### Radius contracts

- `--oneday-radius-control`: highlighters, segmented buttons, drag grips, and
  compact icon buttons. It follows Obsidian `--button-radius`.
- `--oneday-radius-surface`: the Oneday block and layout slots. It intentionally
  aliases the control radius so themes cannot make the main geometry look
  unrelated to the approved highlighter and grip geometry.
- `--oneday-radius-group`: outer grouped-control shells, one step above their
  children.
- `--oneday-radius-data`: Stats tracks and bars only. Data geometry remains
  tighter than interactive geometry.
- Menus, tooltips, and popovers remain elevated Obsidian surfaces and use
  `--radius-m`; they are not layout slots or compact controls.

### Neutral-surface contracts

- `--oneday-surface-control`: highlighters plus Settings/More icon buttons.
- `--oneday-surface-handle`: drag grips; opaque enough that content never shows
  through the handle.
- `--oneday-surface-group`: the outer record/plan visibility group.
- `--oneday-surface-data-track`: Stats bar tracks.

### Content-inset contracts

- `--oneday-content-inset`: the shared left/right inset for Quick Input,
  Highlighters, Text, and Stats slots. It is derived from the drag-grip width
  and overhang so content aligns without being covered when the grip appears.
- The timeline is excluded because its hour labels, track, and annotation lane
  use an SVG coordinate system; its geometry must not inherit content padding.

### Vertical-rhythm contracts

- `--oneday-slot-padding-block` is the shared top/bottom inset for ordinary
  layout slots. Components must not add a one-off top or bottom margin to
  simulate alignment.
- Dialog and Stats content split any spare grid-row height evenly when their
  content fits. The category toolbar is anchored to the shared top inset and
  grows only downward, so switching tools or changing category count never
  moves its creation controls. The visual top and bottom gaps of centered
  content may differ by at most 1 CSS px from browser rounding.
- List-backed component empty actions (Habits and Todos) preview exactly one
  real item row: transparent fill, one dashed neutral border, and the same
  measurable height as a populated row. They must not imply that one new item
  will occupy the full empty component.
- Habit items are compact outlined status rows: one neutral 1px border, no
  shadow, and no filled card surface. Their read-only status is rendered as a
  text badge two pixels shorter than `--oneday-compact-control-height`, leaving
  a quiet vertical inset inside the row. The status owns the row's right edge;
  maintenance actions live in the row context menu rather than reserving space
  for an ellipsis button. Incomplete automatic habits must not use a hollow
  circle or checkbox-like affordance; only completed status may carry a check.
- Todo items are quiet flat rows: no persistent card border or divider. Manual
  ordering is exposed by a left-edge grip only on row hover/focus, and row
  maintenance actions live in the context menu. Grouping and sorting are
  block-local view rules, not fields the user must choose while creating an
  item. Derived grouped/sorted views do not advertise manual drag ordering and
  explain that manual order restores drag. Entering a derived view never mutates
  the authored manual order, so returning to the flat manual view restores it.
- Habit rows use the same hover/focus-only left-edge grip as Todo rows. A habit
  drag updates the global rule order; all dates render that persisted order.
  Habits not visible on the current date keep their relative global positions.
- Habit and Todo row grips reuse the element-slot grip's exact 2 × 3 dot
  geometry. Their row-level chrome stays transparent and borderless; during
  ordering, the full row follows the pointer and the source slot remains as a
  placeholder until drop or cancellation. Row grips float inside the shared
  component gutter instead of occupying a content-grid column, so the hidden
  resting state never leaves a blank leading column or shifts row content.
- Todo estimate is user-authored source data. Plan bindings represent scheduled
  placement and actual bindings represent elapsed work; neither may overwrite
  the stored estimate. Row maintenance exposes the shared compact Todo form
  through the context menu instead of introducing a second settings surface.
- Centering is `safe`: once content overflows, it starts at the top and remains
  fully reachable by the slot's native scroll owner. Empty states continue to
  fill their slot and own the slot border directly.

### Iconography contracts

- Use Obsidian's Lucide set rather than custom SVG or text glyphs.
- Compact secondary actions should have comparable visual density: use
  `settings` for global Oneday settings and `ellipsis` for the block's More
  menu.
- A component header exposes one action per destination. The Habit header uses
  one `pencil` action for editing its items; its empty-state plus remains the
  contextual creation prompt rather than duplicating the header action.
- The Todo header exposes grouping, sorting, and creation as three separate
  compact actions. Grouping and sorting each open only their own choices; they
  must not collapse back into an ambiguous generic settings menu.
- The accessible name describes the action and remains independent of the icon.

Do not fade an entire neutral control with `opacity`: it changes the perceived
surface color by blending it with whatever sits behind the control. Keep the
shared neutral surface opaque and reduce emphasis through foreground color.

State colors are separate from neutral surfaces: accent backgrounds and borders
communicate selection, hover communicates affordance, and neither creates a new
neutral gray role. Validate every token change in light and dark themes, plus
narrow layout, hover, active, and overflow states.

For creation controls, neutral state borders stay transparent. The geometry
tool group uses its neutral fill for structure, while a selected category may
use the accent border to communicate the active drawing type.

Creation uses one primary tool choice and one secondary modifier: `Time span`
and `Time point` are the visible geometry tools (中文：`时间段 / 时间点`); one
fixed `Plan mode` switch controls
whether the result is a plan. Off means the default record mode, while on means
plan mode. The switch label never changes with its state, and record/plan must
not reappear as a second segmented control or redundant status line.
Category symbols mirror the resulting semantics:
period versus line for geometry, solid versus dashed for record versus plan.
Time spans and time points own separate category sets. Switching geometry
replaces the second-row choices in place; it never mirrors, merges, or silently
falls back to the other set. An empty set keeps the geometry controls visible
and turns only the category row into its focused add-first-category entry.
Creation tools occupy their own first row. Time categories always begin at the
left edge of a fresh second row and wrap only within that category row; a lone
category never fills leftover space beside the tool and plan controls.
The first row is titled `Add to timeline` (中文：`添加到时间轴`). The geometry
selector follows that title, while Plan mode is anchored to the far right of
the same row. The title reuses the same typography token as Habit and Todo
component titles. Plan mode has no decorative leading divider; spacing and
alignment alone express the separation. This hierarchy remains stable across themes and container widths;
categories never rise into the first row.

### Scroll ownership contract

Nested scrolling uses native edge handoff rather than trapping wheel input:
component content scrolls first, then the Oneday block viewport, then the
Markdown page. Do not apply `overscroll-behavior: contain` to those scroll
owners.

### Interaction layer contract

Block-level Settings/More actions sit above component slots, drag grips, and
resize hit areas, while menus and popovers remain above the block actions. A
visible block action must own pointer hit testing across its entire button box.
- The block More menu keeps component visibility separate from destructive
  actions. `Delete this Oneday block` is one warning-styled final item; it
  removes only the current fenced block and remains undoable in a source view.
- Slot move/resize previews are painted inside the slot border box. Preview
  chrome must not depend on overflow outside row 0 or the scroll viewport, and
  must not alter the slot's measured geometry.
- Block source mode is a reversible editor plane over the existing visual
  viewport. The plane is anchored to the top of the block and sized by its
  content: at least 320px (or the whole block when shorter), never taller
  than the block; longer drafts scroll inside the editor instead of
  stretching four lines of source across the whole block. The visual block
  that stays visible below it is inert context while a draft is open. The
  plane shows the complete `timeline` fence while keeping the fence
  lines immutable and edits only the block body. Drafts are explicit-apply,
  never blur-save; parser errors and externally changed Markdown fail closed
  while preserving the draft. One Apply equals one Markdown transaction so the
  entire source edit is immediately undoable.

### Focused settings contract

- Component-local setup actions open a focused editor for that product concept:
  Habits open Habit settings and Categories open Time categories. They do not
  drop the user at the top of the global Oneday settings page.
- Focused editors and the global settings page reuse the same renderer and save
  path, so there is only one data model and no synchronization step.
- Global settings presents cross-date Todo goals under the broader concept
  “Todo rules”; it does not promote “weekly cumulative todos” into a separate
  product area. Timeline range and hour-height defaults live under their own
  “Timeline” section and must never visually inherit the Todo-rules heading.
- Rule fields always have visible labels. Goal cadence and appearance cadence
  must not be presented as two indistinguishable values; weekly cumulative
  goals expose an explicit weekly recurrence choice instead of reusing the
  daily appearance schedule. A one-off weekly goal is scoped to one natural
  Monday-through-Sunday week.
- Habit settings keep two independent questions explicit: the appearance
  schedule answers “on which dates is this row shown”, while the completion
  condition answers “what progress completes it”. Appearance supports every
  day, workdays, selected weekdays, every N days from a stable anchor, and an
  interactive list of calendar dates. Completion supports any matching record,
  daily/weekly duration, and a weekly completion count. Weekly count contributes
  at most once per calendar date and ignores plan blocks.
- Habit duration is stored canonically in minutes while the editor may display
  either minutes or decimal hours. Switching units never changes the stored
  duration (for example, 30 minutes equals 0.5 hours).
- A category selector carries the selected category's circular color marker.
  The focused category editor uses compact outlined rows, no full-width row
  dividers, two columns when space permits, and one column in narrow dialogs.

### Timeline range-boundary contract

- The timeline SVG is an interaction canvas, not selectable document text.
  Creating, moving, or resizing an entry must never leave hour labels, duration
  copy, or notes in the browser's native text-selection state; editable text
  panes outside the SVG keep normal selection behavior.
- The visible top and bottom track lines and every point inside the track belong
  only to time-block creation. The shared five-minute snap may resolve a start
  to the exact range boundary (for example, 07:00).
- Each edge has two compact buttons painted fully outside the track: `−1 hour`
  contracts inward and `+1 hour` extends outward. The painted button rectangle
  is the complete pointer hit area and uses a pointer cursor; no unrelated
  transparent edge lane may impersonate either action.
- Contraction fails closed when it would hide an existing span or time point.
  Range buttons remain available when no category is configured or visible;
  only block creation is disabled in that state.
